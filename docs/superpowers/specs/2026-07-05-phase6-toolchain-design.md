# Phase 6: Toolchain & CLI — Design

Approved 2026-07-05. Builds on phase 5 (`feature/fable-new-vision`, through
commit `b179349`). One spec covers the whole phase per user decision; the
implementation plan may stage it internally (carry list → CLI skeleton →
dev server → hot reload → templates → containers).

## 1. Scope

**In:**
- `swiftwui` CLI: `init`, `dev`, `build`, `ssg`, `serve`.
- Pure-Swift dev server (POSIX sockets, localhost, static files + SSE).
  Zero npm anywhere in the toolchain.
- Hot reload: file watcher → wasm rebuild → browser reload **with @State
  preserved** via the phase-5 snapshot machinery.
- Project templates: `basic`, `mvvm`, `tca` (TCA-style store, no external
  package).
- Containers: build Dockerfile + deploy (nginx) Dockerfile, generated by
  `init`.
- Phase-5 carry list (Task 1, §11).
- First mandatory in-phase browser acceptance (also closes the phase-5
  manual-check debt).

**Out (deferred):**
- brew/mint distribution; the CLI is `swift run swiftwui` / a locally built
  binary this phase.
- True HMR (wasm module swap without page reload) — research-grade for
  Swift/wasm, not attempted.
- Vite interop or any Node-based path.
- SSR daemon, deployment orchestration beyond the two Dockerfiles
  (no compose/k8s).
- `init --force` into non-empty directories.

## 2. Context — what this builds on

- The JavaScriptKit **PackageToJS** plugin (`swift package --swift-sdk … js`)
  already produces a working bundle in `.build/plugins/PackageToJS/outputs/Package/`
  (`index.js`, `instantiate.js`, `runtime.js`, `platforms/browser.js`,
  `<App>.wasm`). Verified: the bundle has exactly **one** bare import —
  `@bjorn3/browser_wasi_shim` in `platforms/browser.js`. That import is the
  only reason Examples need Vite today. A browser **import map** pointing at
  a vendored copy of the shim removes the Node dependency entirely.
- Phase 5 shipped the full snapshot pipeline: `StateStore` encodes snapshot
  rows (canonical `NodeIdentity` keys, `_TypeNameRegistry`, non-serializable
  degrade with warning) and `DOMRuntime` seeds state from an embedded
  snapshot before first resolve, with cold-render fallback on mismatch.
  State-preserving reload is a thin second transport over this machinery.
- The dual-entry pattern (wasm mount / native `ssg` subcommand in one
  executable) is proven by the TodoMVC example; templates reproduce it.
- Toolchain pin: Swift 6.3.3 + `swift-6.3.3-RELEASE_wasm` SDK, versions must
  match exactly (CLAUDE.md).

## 3. Module layout & dependencies

Same `Package.swift`, two new targets:

- **`SwiftWUIToolchain`** (library, native-only): HTTP server, SSE, file
  watcher, scaffolder, template store, subprocess orchestration. All logic
  lives here so the native test suite covers it.
- **`swiftwui`** (executableTarget, product `swiftwui`): thin
  swift-argument-parser command definitions delegating to Toolchain.

New dependency: `swift-argument-parser` (`from: "1.3.0"`; Apple, zero
transitive deps). No SwiftNIO — the dev server is hand-rolled on POSIX
sockets, which is sufficient for a localhost single-developer tool.

Vendored asset: `@bjorn3/browser_wasi_shim` **0.3.0** (MIT, ~3 JS files +
LICENSE) as SwiftPM resources of the `swiftwui` target (`Bundle.module`),
alongside the dev-client JS and templates. Pinned by copy; upgrading it is a
deliberate vendoring commit.

Subprocesses (`swift package js`, `swift run`, `swift sdk list`) go through a
`ProcessRunner` protocol; tests inject a mock, production uses
`Foundation.Process`.

## 4. Command surface

| Command | Behavior |
|---|---|
| `swiftwui init <Name> [--template basic\|mvvm\|tca] [--swiftwui-path <dir>]` | scaffold a new project into `./<Name>/` (must not exist / be empty) |
| `swiftwui dev [--port 8080] [--swift-sdk <id>]` | debug wasm build → serve → watch → reload loop |
| `swiftwui build [-c debug\|release] [--out dist] [--swift-sdk <id>]` | wasm bundle + index.html + vendored shim → `dist/` |
| `swiftwui ssg [--out dist] [--product <name>]` | wrapper over `swift run <App> ssg --out <dir>` (dual-entry pattern) |
| `swiftwui serve [dir] [--port 8080]` | static preview of a built `dist/`, no watcher, no injection |

- `dev`/`build` shell out to the proven
  `swift package --swift-sdk <id> js -c <config>`. The CLI knows nothing
  about compilation internals.
- Default `--swift-sdk`: auto-detect from `swift sdk list` (first installed
  SDK whose id contains `wasm`); explicit flag overrides. No SDK installed →
  actionable error (§10).
- `ssg` resolves the executable via `swift package describe --type json`
  (first executable target; `--product` overrides) and runs it natively.

### Output layout contract (dev/prod parity)

Template `index.html` uses **relative** URLs that work identically in dev
and in `build` output:

```html
<script type="importmap">
{"imports": {"@bjorn3/browser_wasi_shim": "./vendor/wasi-shim/index.js"}}
</script>
<script type="module">
  import { init } from "./app/index.js";
  await init();
</script>
```

- `build` lays out `dist/index.html`, `dist/app/` (PackageToJS output copied
  verbatim), `dist/vendor/wasi-shim/`.
- `dev` serves the same URL space virtually: `/app/*` from the plugin output
  dir, `/vendor/wasi-shim/*` from bundled resources, `/` from the project's
  `index.html` with dev-client injection (§6). No files are written into the
  user's project by `dev`.
- `swiftwui ssg` after `build` emits pages into the same `dist/`; hydrate
  mode points `wasmScriptPath` at `/app/index.js` (the `cssFile`
  root-absolute-href carry item lands in Task 1 and keeps subdirectory
  deploys in mind).

## 5. Dev server

- HTTP/1.1 over POSIX sockets, bound to `127.0.0.1` only. GET/HEAD only;
  no TLS, no HTTP/2, no range requests.
- Correct MIME table (html, js, mjs, css, wasm, json, svg, png, jpg, ico,
  map, txt); `application/wasm` is load-bearing for streaming instantiation.
- Reload channel: **SSE** (`GET /__swiftwui/events`), not WebSocket.
  Rationale: SSE is a plain HTTP stream — no upgrade handshake, no frame
  masking to implement on raw sockets; browser `EventSource` auto-reconnects
  after CLI restarts. Events: `reload` (empty payload) and `build-error`
  (payload: compiler output, JSON-encoded).
- Reserved URL namespace `/__swiftwui/*`: `events`, `dev-client.js`,
  `vendor/wasi-shim/*` also aliased here for injection independence.

## 6. Watch → rebuild → reload loop

- Watcher: mtime polling of `Sources/**/*.swift`, `Package.swift`,
  `index.html`; 500 ms interval, 200 ms debounce after last change.
  Cross-platform by construction (no FSEvents/inotify forks).
- On change: run `swift package js` once (queue collapses further changes
  into one pending rebuild).
  - Failure → emit `build-error`; the dev client shows a full-screen overlay
    with the compiler output; the page stays alive; next change retries.
  - Success → emit `reload`.
- Dev client (`/__swiftwui/dev-client.js`, injected into the served
  `index.html` at response time — right after `<head>`, or prepended when no
  `<head>` exists):
  1. opens the `EventSource`;
  2. on `reload`: dispatches a `swiftwui:dev-snapshot-request` `CustomEvent`
     on `window` (synchronous), then calls `location.reload()`;
  3. on `build-error`: renders/updates the overlay; clears it on next
     successful load;
  4. sets `window.__swiftwui_dev = true` before the app module loads
     (injection order guarantees this).

## 7. State-preserving reload (the only framework change)

Two small, dev-gated hooks in `SwiftWUIDOM` — production behavior without
the dev flag is byte-identical to phase 5:

- **Save:** when `window.__swiftwui_dev` is set, `DOMRuntime` registers a
  listener for `swiftwui:dev-snapshot-request`; the handler synchronously
  encodes the live `StateStore` snapshot (same encoder as SSG, same
  non-serializable degrade semantics) and writes the JSON string to
  `sessionStorage["__swiftwui_dev_snapshot"]`. The dev client reloads only
  after the synchronous dispatch returns.
- **Seed:** at boot, snapshot sources in priority order: (1) embedded SSG
  `<script>` snapshot (unchanged phase-5 path), (2) if `__swiftwui_dev`,
  `sessionStorage["__swiftwui_dev_snapshot"]` — read, seed, then delete the
  key. Malformed JSON or identity/type mismatch after a code edit degrades
  exactly like phase-5 hydration: skip row / cold render, console warning,
  never trap.

No new public API; both hooks ride existing snapshot encode/seed SPI.

## 8. Templates (`swiftwui init`)

Stored as plain files under the `swiftwui` target's resources
(`Templates/<name>/…`), copied with `{{NAME}}` substitution (project name,
target name; applied to file contents and to path components). Readable and
diffable as normal files — no string-literal embedding.

Every template produces:

```
MyApp/
  Package.swift          # SwiftWUI via git URL + branch; --swiftwui-path → path dependency
  Sources/MyApp/         # dual entry: wasm mount / native `ssg` subcommand
  index.html             # relative-URL contract from §4
  Dockerfile             # build container
  Dockerfile.deploy      # nginx deploy container
  .gitignore             # .build, dist, .swiftpm
  README.md              # dev/build/ssg/docker walkthrough
```

Three templates, identical user-visible app (counter + About page with
Router) so the architectures are directly comparable:

- **basic** — logic straight in `Tag` bodies with `@State`; the newcomer
  entry point, minimum files.
- **mvvm** — observable `ViewModel` classes own state and intent methods;
  Tag views are logic-free. Shows the separation pattern on SwiftWUI
  reactivity.
- **tca** — hand-rolled `Store<State, Action>` + pure reducer function;
  views `store.send(...)`. Zero external packages; README states explicitly
  this is *TCA-style*, not pointfree TCA (which does not build on wasm).

Acceptance gate: each template must build natively, build for wasm, and run
`ssg` successfully.

## 9. Containers

Two Dockerfiles per template:

- **Dockerfile** (build): multi-stage; base `swift:6.3.3`, installs the
  matching wasm SDK, runs `swiftwui build` + `swiftwui ssg`; final stage
  contains only `dist/`. Reproducible builds for CI and contributors without
  local swiftly setup.
- **Dockerfile.deploy**: `nginx:alpine`, `COPY dist/`, nginx config with
  `application/wasm` MIME and MPA-friendly fallback routing.

No docker-compose, no orchestration.

## 10. Error handling

- Port busy → clear message naming the port + `--port` hint. No
  auto-increment (surprise ports are worse than an error).
- `swift` missing or no wasm SDK installed → preflight `swift sdk list`
  before first build; error includes the exact `swift sdk install …` command
  for the pinned version.
- `init` target dir exists and is non-empty → refuse.
- Compiler errors in `dev` → terminal passthrough + browser overlay (§6);
  server keeps running.
- Broken/mismatched dev snapshot → console warning + cold render (§7);
  never a trap.
- Subprocess exit codes surface verbatim; CLI exit code mirrors the failed
  step.

## 12. Testing & acceptance

**Native gate (primary, as always):**
- HTTP server: request→response over a loopback socket — MIME table, 404,
  HEAD, SSE stream framing, dev-client + import-map injection points.
- Watcher: temp dir, touch → event, debounce collapse.
- Scaffolder: `init` into temp dir — file structure, `{{NAME}}`
  substitution, all 3 templates; refusal on non-empty dir.
- Snapshot save/seed hooks: unit-level on MockBackend where possible; the
  wasm-side listener is exercised in the browser check.
- Subprocess orchestration via mocked `ProcessRunner` (SDK detection,
  build-failure propagation, ssg product resolution).

**Heavy gates (manual / CI-optional):**
- Per template: native `swift build`, wasm build, `ssg` run — required
  before phase close.
- Docker: build image produces `dist/`; deploy image serves it.

**Browser acceptance (mandatory this phase; also closes phase-5 debt):**
- Phase-5 items: `data-swui-hydrated` marker, two-button dispatch, About
  snapshot-restore probe, MPA static nav, viewport after hydration.
- Phase-6 items: full dev cycle — edit a `.swift` file, auto rebuild,
  reload with counter state preserved; build-error overlay appears and
  clears; `swiftwui serve` of a built site works without the dev client.

## 13. Decision log

- **D1** Whole phase in one spec (user decision; implementation plan may
  stage internally).
- **D2** Pure-Swift dev server; zero npm in the toolchain.
- **D3** Dependencies: swift-argument-parser only; no NIO; POSIX-socket
  server.
- **D4** Hot reload = rebuild + full page reload with @State snapshot
  restore over sessionStorage; no true HMR.
- **D5** Templates: basic + mvvm + tca-style (hand-rolled store, external
  TCA explicitly out).
- **D6** Containers: build Dockerfile + nginx deploy Dockerfile, generated
  by `init`.
- **D7** CLI is a thin orchestrator shelling out to PackageToJS / `swift
  run`; no libSwiftPM linkage; no SwiftPM command plugins (sandbox blocks
  the server, `init` impossible outside a package).
- **D8** SSE over WebSocket for the reload channel.
- **D9** mtime polling watcher (cross-platform, no platform forks).
- **D10** Vendored `browser_wasi_shim` 0.3.0 resolved via browser import
  map; dev/prod URL parity through the `./app/` + `./vendor/` layout
  contract.
