# Dependencies

A small dependency-injection layer for the code the render tree doesn't
reach — services, models, and closures that need a real implementation in
production and a fake one in tests.

## Overview

``Environment`` carries values *down the render tree*: a component reads
`@Environment(\.webSession)` because it sits somewhere under a mounted
runtime that put a session there. A plain service class has no position in
that tree and nothing to read from. ``Dependency`` fills that gap — it
resolves from a process-wide store rather than from a parent node, so it
works in a `Tag`, in an `@Observable` model, inside an escaping closure, and
inside a detached `Task`.

Three pieces: ``DependencyKey`` declares a dependency and its defaults,
``DependencyValues`` is the keyed collection your app extends with computed
properties, and ``Dependency`` reads one. ``withDependencies(_:operation:)``
and ``prepareDependencies(_:)`` override them.

The whole store is `@MainActor`-isolated. Every target generated by
`swiftwui init` sets `.defaultIsolation(MainActor.self)`, so a plain
`final class` reading `@Dependency` compiles with no annotation; a target
that doesn't opt into module-wide main-actor isolation needs an explicit
`@MainActor` on the reader.

## Declaring a dependency

A key supplies `liveValue` — the production default — and optionally
`testValue`. Then extend ``DependencyValues`` with a computed property, the
same shape as an `EnvironmentValues` extension:

```swift
@MainActor
final class ArticleService {
    @Dependency(\.webSession) var session
    @Dependency(\.logger) var logger

    struct Article: Decodable { let id: Int; let title: String }

    func latest() async -> [Article] {
        do {
            return try await session.json(from: "/api/articles", as: [Article].self)
        } catch {
            logger.error("articles failed: \(error)")
            return []
        }
    }
}

struct ArticleServiceKey: DependencyKey {
    static var liveValue: ArticleService { ArticleService() }
}

extension DependencyValues {
    var articleService: ArticleService {
        get { self[ArticleServiceKey.self] }
        set { self[ArticleServiceKey.self] = newValue }
    }
}
```

`testValue` defaults to `liveValue`, so a key that has nothing special to say
about tests omits it — as `ArticleServiceKey` does above, because the service's
own `@Dependency(\.webSession)` already resolves to a session that refuses
network access under tests.

### How the test value is picked

``DependencyKey/testValue`` is substituted automatically when the process is a
test run. The detection is a one-time probe: `dlsym` for Swift Testing's stable
ABI entry point (`swt_abiv0_getEntryPoint`), falling back to XCTest's
`XCTestConfigurationFilePath` environment variable. There is no flag to set and
nothing to configure. On wasm the probe is compiled out and always reports
false — tests never run there.

The probe result and each key's resolved default are computed **once per
process and cached for its lifetime**. Two consequences follow:

- A `DependencyKey` whose `Value` is a reference type is a singleton. Two
  independently constructed models resolving the same key get the same
  instance, even though `liveValue` looks like it builds a fresh one on every
  read.
- A default resolved *before* whatever it wraps is configured stays wrong
  forever. That is exactly what happens to `\.webSession`, whose `liveValue` is
  a `WebSession.shared` passthrough: a read during the first render, before
  `WebSession.bootstrap(_:)` has run, caches `.unsupported` permanently. The
  DOM boot path papers over this by installing an explicit override that
  shadows the poisoned cache — see the built-ins below.

## Reading a dependency

`@Dependency(\.key)` works wherever you can declare a stored property. Inside
a component:

```swift
struct ArticleList: Tag {
    @Dependency(\.articleService) var service
    @State private var titles: [String] = []

    var body: some Tag {
        Div {
            Button("Load") {
                Task { titles = await service.latest().map(\.title) }
            }
            Ul { ForEach(titles, id: \.self) { title in Li { Text(title) } } }
        }
    }
}
```

and, identically, in a model that has no place in the tree at all:

```swift
@MainActor
final class CheckoutModel {
    @Dependency(\.navigate) var navigate
    @Dependency(\.webStorage) var storage
    @Dependency(\.logger) var logger

    func complete(orderID: String) {
        storage.set("checkout.lastOrder", orderID)
        logger.info("order \(orderID) complete")
        navigate("/orders/\(orderID)", replace: true)
    }
}
```

## Resolution order

Every read walks three tiers, in this order:

1. **The overrides captured when this wrapper was initialized.** ``Dependency``
   snapshots the whole override collection in its `init`.
2. **The current global overrides** — everything `prepareDependencies` has
   installed, plus any `withDependencies` scope active at the moment of the
   read.
3. **The key's cached default** — `testValue` under tests, `liveValue`
   otherwise.

Step 1 is the one that earns its keep. Without it, an override would only apply
to reads that happen *synchronously inside* the scope, which excludes almost
everything a service actually does: escaping closures, `Task { }` bodies,
callbacks that fire after the scope has long returned. Because the snapshot
travels with the object, a model built inside a scope keeps its mocks
everywhere, forever:

```swift
var lines: [String] = []
let service = withDependencies {
    $0.logger = Logger { level, message in lines.append("\(level.rawValue): \(message)") }
} operation: {
    ArticleService()
}

service.logger.info("recorded")   // still the capturing logger, outside the scope
```

The mirror image is worth internalizing too. A snapshot only contains the keys
that were overridden *at the moment of init*; tier 2 fills in the rest at read
time. So a model constructed before any override of `\.logger` exists picks up
a later `prepareDependencies` change to it, while a model constructed after one
keeps that first value and ignores every subsequent global change to the same
key. Same override call, two different-looking outcomes, decided entirely by
when and where the object was created.

## Scoped versus permanent overrides

``withDependencies(_:operation:)`` saves the current overrides, applies your
mutations, runs `operation`, and restores on the way out — including on a
thrown error. It nests: an inner scope's mutation is undone when the inner
scope exits, leaving the outer scope's in place.

It is **synchronous only**. There is no `async` overload, and one would not
help: the point is not to await inside the scope but to *construct* inside it.
Build the objects under test in `operation` and let their snapshots carry the
overrides into whatever async work they do later.

```swift
let service = withDependencies {
    $0.webSession = WebSession(transport: FixtureTransport())
} operation: {
    ArticleService()
}
let articles = await service.latest()   // fixture transport, outside the scope
```

Reading a value inside the mutate closure returns the currently effective one,
which is how you decorate rather than replace:

```swift
withDependencies {
    let base = $0.logger
    $0.logger = Logger { level, message in base.handler(level, "[checkout] \(message)") }
} operation: {
    CheckoutModel()
}
```

``prepareDependencies(_:)`` is the permanent form — no save, no restore. It is
for app startup, staging configuration, and SSG stubs:

```swift
prepareDependencies {
    $0.logger = Logger { level, message in remoteLog(level.rawValue, message) }
}
```

**Calling `prepareDependencies` inside an active `withDependencies` scope is
silently reverted when that scope exits.** Its mutation lands on the copy that
the scope's save/restore then discards, so "permanent" becomes "until this
scope returns". Call it outside scopes — at the entry point, before any scope
opens.

There is no public reset. Overrides accumulate for the process lifetime, which
is the intended behavior for an app entry point and a reason to prefer
`withDependencies` in tests, where per-test isolation is what you want anyway.

## The built-ins

Four keys ship with the framework:

| Key | Default outside a booted app | After DOM boot |
| --- | --- | --- |
| `\.webSession` | `WebSession.shared` (`.unsupported` in tests) | the runtime's own session |
| `\.navigate` | no-op | pushes to the live router |
| `\.webStorage` | in-memory store | backend-wired, shared with `@AppStorage` |
| `\.logger` | prints `[level] message` | unchanged |

Three of them — `\.webSession`, `\.navigate`, `\.webStorage` — are rewired to
the live runtime by ``Runtime/bootstrapDependencies()``, which the DOM entry
point calls once at boot. `\.logger` has no runtime backing and keeps its
print-based default until you override it.

`bootstrapDependencies()` is deliberately **not** called from `mount()`.
Constructing or mounting a bare `Runtime` must never touch process globals, or
native tests that build their own runtimes in parallel would overwrite each
other's store. Only real platform entry points call it — which means SSG does
not: during a static build `\.navigate` is a no-op and `\.webStorage` is an
in-memory store whose writes go nowhere. `\.webSession` is the exception, since
`SwiftWUIStatic` bootstraps `WebSession.shared` before rendering starts.

`\.webSession`'s `testValue` is `WebSession.unsupported`, so every unmocked
request in a test throws `WebFetchError.unsupported` rather than reaching the
network. Override it with `withDependencies` to supply a fixture transport.

``WebStorage`` is the imperative, non-reactive counterpart of `@AppStorage` —
`get`/`set`/`remove`, with a `kind:` parameter selecting `localStorage`
(`.local`, the default) or `sessionStorage` (`.session`):

```swift
let lastOrder: String? = storage.get("checkout.lastOrder")
storage.set("wizard.seen", true, kind: .session)
```

Writes go through the same store `@AppStorage` reads, so a `WebStorage` write
does re-render every `@AppStorage` component bound to that key. The storage
itself is plaintext and readable by any script on the origin — never put
secrets, tokens, or session identifiers in it. The `__swiftwui.` key prefix is
reserved; using it logs a warning rather than failing.

Inside a component's `body`, prefer the environment channel where one exists:
`@Environment(\.webSession)` and `@Environment(\.navigate)` read the runtime's
values directly, and `@Environment(\.navigate)` additionally picks up the
ambient page transition that `@Dependency(\.navigate)` cannot see, having no
position in the tree. The dependency keys are for everything outside it.

## `@Dependency` is not reactive

Changing a dependency never re-renders anything. There is no observation on the
store, no invalidation, no dirty marking — a `withDependencies` or
`prepareDependencies` call mutates a dictionary and returns. A component that
reads `@Dependency(\.articleService)` in its `body` and then has that key
overridden keeps rendering with whatever it resolved last, until something else
invalidates it.

This is a design decision, not a gap. Dependencies are the app's wiring: which
API client, which logger, which navigation implementation. That wiring is
chosen at startup and in tests, not flipped mid-frame, and making every read a
tracked observation would put a re-render hazard on every service call for no
benefit.

The split to keep in mind:

- **`@Environment` for values that change while the app runs** and whose change
  must be reflected on screen — `\.colorScheme`, `\.isOnline`, `\.media`,
  `\.routeInfo`. These are tracked, and only when read inside a component's
  `body` (see <doc:BrowserAPIs>).
- **`@Dependency` for implementations that are chosen once** and swapped in
  tests — API clients, loggers, anything you would otherwise pass through
  fifteen initializers to reach the one object that needs it.

If a dependency's *data* needs to drive the UI, put the data in `@State` or in
an `@Observable` model the component reads, and keep the dependency as the
thing that fetches it. That is what `ArticleList` above does: the service is a
dependency, the titles it returns are `@State`.
